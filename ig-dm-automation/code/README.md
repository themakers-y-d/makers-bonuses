# code

כל הקוד של המערכת, מוכן לפריסה. אין תלויות npm ואין framework: פונקציות Node רגילות שרצות על Vercel.

## מה יש כאן

`api/ig-webhook.js` היא נקודת הקצה שמטא פונה אליה. GET הוא לחיצת היד של רישום ה-webhook, POST הוא עיבוד האירועים.

`api/ig-poll.js` היא הסורק: מושך תגובות חדשות מהמדיה של החשבון ומריץ עליהן את אותו מנוע. זה המסלול שעובד מיד, בלי אישור מיוחד ממטא.

`api/_ig-graph.js` עוטף את קריאות ה-Graph API: קריאת הטוקן, הודעה פרטית, הודעה רגילה ותגובה פומבית.

`api/_ig-rules.js` מנרמל טקסט עברי ומתאים אותו לכללים.

`api/_ig-store.js` הוא שכבת בסיס הנתונים המשותפת לשני המסלולים, כולל מנגנון מניעת הכפילויות.

`api/ig-refresh.js` מחדש את טוקן ה-Graph מהענן. הטוקן חי 60 יום; נקודת הקצה נקראת פעם ביום מהענן, וכשנשארו פחות מעשרה ימים היא מחליפה אותו בטבלה. ככה המערכת לא תלויה בשום מחשב דלוק, וגם לא נשברת בשקט אחרי חודשיים.

קבצים שמתחילים בקו תחתון בתוך api אינם נחשפים ככתובת אינטרנט. זו התנהגות של Vercel ולא מקרה.

`supabase/migrations/001_ig_automation.sql` יוצר את ארבע הטבלאות. להריץ פעם אחת ב-SQL Editor של הפרויקט.

`scripts/ig-poll-ping.sh` מפעיל את הסורק ממחשב מקומי. `scripts/refresh-ig-token.sh` מחדש את הטוקן כשנותרו פחות מעשרה ימים לתפוגה. שניהם מקבלים נתיב לקובץ env כארגומנט ראשון.

`.github/workflows/poll.yml` מפעיל את הסורק מהענן כל כמה דקות, בלי תלות במחשב דלוק. דורש סוד בשם IG_POLL_SECRET ברמת הריפו.

`.github/workflows/refresh.yml` קורא ל-`api/ig-refresh` פעם ביום עם אותו סוד, ושומר על הטוקן חי לתמיד. אחרי הפריסה יש לעדכן בשני הקבצים את כתובת הפרויקט.

`.env.example` הוא רשימת כל משתני הסביבה עם הסבר לכל אחד ואיפה למצוא אותו.

## התקנה מהירה

`scripts/setup.sh` עושה את רוב ההתקנה לבד: אוסף את הערכים, מאמת את הטוקן מול מטא, מקים את הפרויקט ב-Vercel, מזין את משתני הסביבה, פורס ומאמת. בטוח להרצה חוזרת.

`scripts/doctor.sh` בודק מערכת מותקנת מקצה לקצה ואומר מה נכשל ומה לעשות. זו הפקודה הראשונה כשמשהו לא עובד.

## פריסה בקצרה

יוצרים ריפו, מעתיקים את התוכן, מריצים `vercel link`, מזינים את משתני הסביבה, ומריצים `vercel deploy --prod`. הפירוט המלא נמצא ברמה שמעל, בקובץ 01-runbook.md.

## אזהרה אחת

אל תשנו את מנגנון ה-claim בטבלת ig_events לפני שקראתם את 02-architecture.md. הוא מה שמונע שליחת הודעה כפולה כשמטא שולחת את אותו אירוע פעמיים, וזה קורה בפועל.
