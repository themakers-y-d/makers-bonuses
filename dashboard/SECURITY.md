# שער האבטחה. לא אופציונלי

כתוב אל הסוכן. קצר בכוונה, והיחיד בערכה שאסור לדלג עליו.

## מה בדיוק מסוכן כאן

הדאשבורד יושב על כתובת באינטרנט, והמפתח הציבורי של הפרויקט נמצא בתוך הקוד של הדף. זה תקין ומתוכנן: המפתח לבדו לא נותן גישה לכלום.

מה שמחזיק את זה הן ההרשאות ברמת השורה. אם הן כבויות, רחבות מדי, או שמישהו הוסיף אובייקט שעוקף אותן, כל אדם שפותח את הדף יכול למשוך את **כל רשימת הלקוחות של הבעלים ואת הסכומים שלהם**.

הכשל הזה שקט לגמרי. מהדפדפן הכל נראה תקין.

## מה אתה חייב לעשות

מיד אחרי `db/schema.sql`, הרץ את `db/verify.sql` באותו מקום.

זו שאילתה אחת שמחזירה תשע שורות, ולא במקרה: עורך ה-SQL של סופאבייס מציג רק תוצאה אחת, וקובץ עם כמה שאילתות היה מראה חלק מהשער ונקרא כאילו כולו ירוק. מאותה סיבה, שאילתת האשם שבסוף הקובץ מוערת, ומסירים לה את ההערה רק בהרצה נפרדת.

**הראה לבעלים את הפלט.** לא לספר לו שזה תקין, להראות לו את תשע השורות. הוא לא חייב להבין אותן, הוא חייב לראות שבדקת.

שורה אדומה אחת: עצור. אל תפרוס, ואל תמשיך. תקן והרץ שוב.

## החור שכולם נופלים בו: View

ב-Postgres, View רץ כברירת מחדל בהרשאות של מי שיצר אותו, ולא של מי שקורא. כלומר הוא **עוקף את ההרשאות ברמת השורה לגמרי**. ובסופאבייס, אובייקט חדש בסכמת public מקבל הרשאת קריאה לאורח באופן אוטומטי.

המשמעות: ברגע שתיצור View נוח לסיכום חודשי, וזה הדבר הכי טבעי בעולם במשימה הזאת, פנייה אנונימית עם המפתח הציבורי תחזיר את כל רשימת הלקוחות. בלי שום סימן.

לכן כל View נוצר ככה, ולא אחרת:

```sql
create view public.monthly with (security_invoker = on) as
  select ... from public.entries;
revoke all on public.monthly from anon;
```

ו-View מוחומר, כלומר `materialized view`, **אסור לגמרי מעל `entries`**. אין לו מנגנון כזה בכלל, והוא שומר את השורות של הבעלים כטבלה שנוצרה בהרשאות היוצר. אין לו תיקון, רק החלפה ב-View רגיל.

בדיקה 7 ב-`verify.sql` סורקת את כל הסכמה ותופסת את שלוש המשפחות: View שעוקף, View מוחומר, וטבלה שנולדה בלי הרשאות ברמת שורה. אל תשתיק אותה. אם היא אדומה, בסוף הקובץ יש שאילתה שנייה שאומרת מי בדיוק האובייקט האשם.

## ארבעה דברים שלעולם לא

לעולם אל תשים את ה-service key בתוך `app/`, בקוד, או בריפו. הוא עוקף את כל ההרשאות. מקומו בקובץ `~/.config/makers-dashboard/supabase.env`, ושם בלבד.

לעולם אל תפתור בעיית הרשאות בכך שתפתח את הטבלה לאורח. אם משהו לא נקרא, הבעיה היא בהתחברות או ב-`grant select` ל-authenticated, ושתיהן נבדקות ב-`verify.sql`.

לעולם אל תיצור View בלי `security_invoker = on`, ולעולם אל תיצור View מוחומר מעל הטבלה הזאת.

לעולם אל תכתוב מדיניות עם `using (true)`. היא נראית כמו מדיניות והיא בעצם פתיחה מלאה לכל משתמש מחובר, וכל אדם שהקליד מייל בדף הוא משתמש מחובר.

ואם אתה חייב פונקציה עם `security definer`, למשל כעזר למדיניות, נקה אותה מיד. **שלילה מאורח לבדה לא עושה כלום**, כי פונקציה נולדת עם הרשאת הרצה לכולם והאורח יורש אותה משם:

```sql
revoke execute on function public.FUNC_NAME() from public;
grant  execute on function public.FUNC_NAME() to authenticated;
```

והשורה השנייה רק אם מדיניות באמת קוראת לה. פונקציה כזאת מחזירה בוליאני, לא שורות. פונקציה שמחזירה שורות היא דלת אחורית לטבלה, ואין לה הצדקה.

ולעולם אל תוסיף טבלה בלי לחזור לכאן. טבלה נולדת בלי הרשאות ברמת שורה, וזו בדיוק הדרך שבה הדאשבורד השני של הבעלים ידלוף.

## כשמוסיפים טבלה או View

אותם ארבעה כללים על הטבלה: `enable row level security`, `force row level security`, מדיניות שמשווה `auth.uid()` לבעלים, ושלילת הרשאות מאורח. ועל View, ה-`security_invoker`.

ואז `verify.sql` שוב, והצגת הפלט לבעלים.

## הערה על כניסה

הדף מבקש קישור כניסה עם `shouldCreateUser: false`. אל תסיר את זה.

בלעדיו, כל אדם שמחזיק את הכתובת יכול ליצור משתמשים בפרויקט של הבעלים ולשרוף את מכסת המיילים, שהיא שניים בשעה, וכך לנעול את הבעלים מחוץ לדאשבורד שלו. ההרשאות ימנעו דליפת נתונים, אבל לא ימנעו את הנעילה.
